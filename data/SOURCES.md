## Как восстановить исходный CSV

Команды ниже выполняются в PowerShell из корня проекта. Если CSV уже есть, повторно скачивать его не нужно: выполните только проверку SHA-256. Для восстановления используется закреплённая версия **4** из манифеста, а не последняя версия набора.

```powershell
$sourceManifest = Get-Content -LiteralPath .\data\kaggle_astana.source.json -Encoding UTF8 -Raw | ConvertFrom-Json
$sourceCsvPath = $sourceManifest.local_file
if (Test-Path -LiteralPath $sourceCsvPath) {
    throw "Исходный CSV уже существует. Перейдите к проверке SHA-256."
}
$sourceArchivePath = Join-Path ([System.IO.Path]::GetTempPath()) ("astana-v4-{0}.zip" -f [guid]::NewGuid())
Invoke-WebRequest -Uri $sourceManifest.download_url -OutFile $sourceArchivePath -ErrorAction Stop
Expand-Archive -LiteralPath $sourceArchivePath -DestinationPath .\data\raw\kaggle_astana -ErrorAction Stop
```

Результат распаковки: `data/raw/kaggle_astana/astana_apartments.csv`. Архив остаётся во временной папке по пути `$sourceArchivePath`. Команды не используют принудительную перезапись; существующий исходный CSV нужно сохранить.

Проверьте исходные байты до запуска очистки:

```powershell
Get-FileHash -LiteralPath .\data\raw\kaggle_astana\astana_apartments.csv -Algorithm SHA256
```

Значение `Hash` должно совпадать с полем `sha256` в [манифесте](kaggle_astana.source.json), независимо от регистра букв:

```text
923bd5483eaea5fdfe9cbf8d36c40ec1875992f66ed70ee29426dd6bc2d189ee
```

Если значение отличается, не используйте файл для воспроизведения результатов: проверьте версию архива и повторите загрузку в отдельную папку. Не открывайте и не пересохраняйте исходник в редакторе таблиц перед проверкой.

## Соответствие признаков проекту

| В проекте | Колонка в скачанном CSV |
| --- | --- |
| Целевая цена в тенге | `price_local` |
| Площадь | `area` |
| Комнаты | `rooms` |
| Этаж | `floor` |
| Этажность | `total_floors` |
| Год постройки | `year_built` |
| Тип дома | `house_type` |
| Состояние | `condition` |
| Район | `district` |
| ЖК | `residential_complex_name` |
| Ссылка | `url` |
| Дата сбора | `parsed_at` |

Описание на Kaggle упоминает `price_kzt`, но **такой колонки в скачанной версии нет**: фактически она называется `price_local`. Есть отдельная цена `price_usd`; медианное отношение `price_local / price_usd` в файле — около 508,913, что согласуется с валютами, указанными автором.

`price_per_m2` в этом CSV соответствует приблизительно `price_usd / area`, то есть это цена за м² в долларах. Не следует принимать её за тенге. При очистке **исключены и `price_usd`, и `price_per_m2`**; в признаки модели они не входят, поскольку содержат информацию о целевой цене и вызвали бы утечку. Приложение рассчитывает цену за м² из прогноза полной цены в тенге и введённой площади.

## Объединённый набор января и марта 2026 года

Для отдельного эксперимента объединены **17 929 очищенных январских** и **3 759 очищенных мартовских** записей: **21 688 → 19 859 строк** после удаления **1 829 предполагаемых дублей**. Исходные raw CSV и обе ранее подготовленные выборки не изменены. Новая выборка сохранена в `data/processed/combined_2026/`; происхождение, контрольные суммы входов и результата — в [отчёте подготовки](../reports/combined_update/preparation_report.json).

`combined_data.py` строит связанные группы сразу по обоим наборам: по нормализованному URL и сочетаниям района, площади, комнат, этажа, этажности, года и адреса либо ЖК. Цена и состояние не входят в ключи сопоставления. Связность транзитивна: если A совпадает с B, а B с C, все три записи входят в одну группу, даже если A и C не имеют общего ключа. Найдено **793 группы с записями обоих периодов**.

В каждой группе сохраняется одна запись. За пределами защищённого test предпочтение отдаётся мартовской записи, затем наибольшему числу заполненных полей среди восьми входов модели, затем меньшему исходному `source_row`. Цена не используется при выборе представителя. Для защищённой группы представитель выбирается только из исходных мартовских test-строк.

Удалено **1 810 январских** и **19 мартовских** записей. По связи удалённой записи с выбранным представителем причины сопоставления распределяются так:

| Вид связи | Удалённых записей |
| --- | ---: |
| Прямое совпадение URL | 668 |
| Прямое совпадение характеристик без цены, без общего URL | 1 125 |
| Только транзитивная связь через другую запись группы | 36 |
| **Всего** | **1 829** |

Это учёт удалённых записей, а не количество независимых квартир с доказанной идентичностью. Совпадения характеристик остаются эвристикой: похожие квартиры могут объединяться, а изменённые адреса и неполные сведения — скрывать повторные предложения.

### Контрольная выборка и происхождение строк

Сохранён ранее зафиксированный мартовский holdout: **594 исходные записи соответствуют 590 группам**. После выбора одного представителя на группу итоговый test содержит **590 строк**, а train — **19 269 строк: 16 119 январских и 3 150 мартовских**. Полные 594 исходные test-записи сохранены отдельно для дополнительного сравнения моделей на неизменном наборе наблюдений.

Все защищённые группы исключены из train. Проверено отсутствие связей этих групп с любыми январскими строками и прежними мартовскими train-строками, а также пересечений ключей и идентификаторов train/test. Обнаружение связи защищённой группы с январём прерывает подготовку до обучения.

В объединённом CSV `source_row` — уникальный номер записи в последовательности «январь, затем март» **до удаления дублей**. Для восстановления происхождения сохранены `dataset_period`, `original_row_index`, `original_source_row` и `record_id`. Итоговый `row_index` в manifest относится к позиции уже в объединённом CSV.

Мартовский период по-прежнему основан на заявлении автора; дат наблюдений по мартовским строкам нет. Предпочтение марта не доказывает более позднюю дату каждого конкретного объявления. Январские даты сохраняют исходный текст без приписывания часового пояса. Даты публикации и скачивания не подставляются вместо дат наблюдений.

Мартовский test уже изучался в предыдущих экспериментах. Это повторно используемый фиксированный ориентир для сравнения, а не новая нетронутая оценка последующих решений. Прежние январские test-строки могут войти в объединённый train, поэтому январский test нельзя использовать для независимой оценки объединённой модели. Для окончательной проверки новых решений потребуется следующий независимый срез.

## Каталог домов и аудит нормализации адресов

Каталог `data/processed/property_catalog/` дополняет **те же 19 859 combined-записей** сведениями из исходных CSV. Привязка raw проверяется по `dataset_period`, `original_source_row`, `record_id` и нормализованному URL. Глобальный `source_row` объединённой таблицы не используется как номер строки raw. Исходные цены, восемь признаков и provenance остаются сохранены; каталог не удаляет объявления и не меняет обучающие данные старых моделей.

Политика v2 нормализует визуально совпадающие латинские `a/c/e/o/p/x/y` только в суффиксах номера дома/корпуса. Улицы и ЖК не транслитерируются, корпуса и дроби не отбрасываются. **35 строк** получили изменённое написание адреса. Приняты **2 группы объединения, включающие 7 объявлений**; **10 групп** отклонены. `нажимеденов 44a`/`нажимеденов 44а` образуют один кандидатный адрес, но противоречащая этажность **9/10/12** запрещает общий `building_id`: записи сохранены отдельно.

При проверке всех кандидатов **1 226 групп / 6 489 строк** имеют конфликты и остаются без уверенного идентификатора дома. Не выбираются большинством спорные ЖК, год, этажность, тип дома или география. Осталось **2 842 группы домов без выявленных конфликтов**, против 4 080 в предыдущей версии; все объявления сохранены. Сопоставление внутреннее: `building_id` не является идентификатором из реестра.

В исходном январском наборе для сохранённых combined-строк есть **16 091 пригодная по bbox пара координат и 28 невалидных пар**. Во всех **3 740 мартовских строках собственные raw-координаты отсутствуют**. В пользовательском каталоге разрешён перенос согласованной географии на 35 мартовских записей; это происхождение явно помечено. Перенос не превращает координаты в собственные наблюдения мартовского источника.

Статус `plausible` означает внутреннюю согласованность архивных точек: минимум две точки, область Астаны, радиус от медианы до 125 м, без невалидных точек, конфликтов и одинакового маркера у разных домов. Он **не означает внешнюю проверку адреса или точность до здания**. Расстояния приблизительные. `raw_*` сохраняют собственные исходные значения и статус `missing/invalid/unverified`; глобальная согласованность и наследование находятся в отдельных полях.

## Источники признаков экспериментальной модели location

`location_model.py` использует отдельную схему 2 с 13 входами: восемь прежних полей, `residential_complex`, `house_key`, `raw_latitude`, `raw_longitude`, `raw_coordinate_status`. `house_key` вычисляется независимо для каждой строки из нормализованных района и явного адреса; глобальные решения каталога о конфликтах его не меняют. Цена, цена за м², идентификатор объявления, каталоговый `building_id`, готовые координаты и статус `plausible` не становятся признаками.

Все зависимости от соседних строк изучаются **только на train внутри каждого CV-разбиения**: проверка конфликтов ЖК/года/этажности, выявление повторных геомаркеров у разных домов, медианная координата дома, импутация и словари категорий. На validation/test используется только обученный справочник. Собственные координаты проверочной строки его не дополняют, новым домам координаты не приписываются; противоречащие обученным сведениям параметры запроса отключают географию этой строки. Таким образом, 35 переносов из полного пользовательского каталога не используются как готовые признаки эксперимента.

Сравниваются восемь базовых признаков, + ЖК, + координаты и + оба признака при одинаковом RandomForest и CV-разбиениях. Выбор выполняется по OOF MAE внутри train; январская и объединённая сохранённые модели сравниваются на общем мартовском holdout. Дополнительная проверка новых домов внутри train диагностическая и не заменяет свежую независимую оценку. Ни один вариант автоматически не активируется в приложении.

Команды из корня проекта:

```powershell
.\.venv\Scripts\python.exe -X utf8 build_catalog.py
.\.venv\Scripts\python.exe -X utf8 property_report.py
.\.venv\Scripts\python.exe -X utf8 location_experiment.py --prepare-only
.\.venv\Scripts\python.exe -X utf8 location_experiment.py --resume
.\.venv\Scripts\python.exe -X utf8 verify_location_experiment.py
```

Первые две команды готовят каталог и отчёт до фиксации эксперимента. `--prepare-only` фиксирует входы, код и split без обучения; `--resume` переиспользует готовые checkpoints и обучает отсутствующие этапы. После фиксации плана каталог, код и источники менять нельзя: подписи должны совпасть. Последняя команда не обучает модели: проверяет SHA-256, происхождение строк, воспроизведение прогнозов и сохранённых метрик, выбор по CV и неизменность январской модели. Метрики диагностики новых домов без повторного fit не воспроизводятся; её разбиение проверяется.

Четыре pipeline и metadata сохранены в `models/location_2026/`, план, checkpoints и итоговый отчёт — в `reports/location_experiment/`. Проверка добавляет `verification.json` и `training_coordinate_audit.csv`. Эксперимент завершён 13 октября 2026 года: по CV выбран + ЖК, его MAE на общих 590 мартовских квартирах — 6,433 млн ₸; совместного варианта ЖК/география — 6,443 млн ₸. Январская и объединённая модели на тех же строках дали 7,579 и 7,183 млн ₸ соответственно. В test согласованные внутри train координаты доступны только для 8 квартир. Метрики и ограничения сохранены в [отчёте](../reports/location_experiment/report.html). Активной остаётся январская RandomForest.


## Поиск независимого среза после марта: 13 октября 2026

Свежая контрольная выборка пока **не собрана**. Подходящий открытый набор среди 14 проверенных источников не подтверждён; это не утверждение об отсутствии таких данных вообще. Новые метрики не рассчитаны. Поиск, даты версий, URL и причины отказа сохранены в [source_research.json](../reports/fresh_validation_2026_10_13/source_research.json), краткий итог — в [отчёте](../reports/fresh_validation_2026_10_13/report.html).

Kaggle по-прежнему публикует январскую v4 и мартовскую v1. Несколько более поздних GitHub-репозиториев содержат точную копию мартовского CSV. У отдельного июньского df_check.csv нет дат наблюдений, URL и адресов для исключения пересечений. Найденные официальные таблицы транзакций Алматы и агрегированные индексы цен не соответствуют задаче проверки отдельных квартир Астаны по ценам предложения.

Диагностический запрос карточки Krisha вернул HTTP 468, массовый сбор не запускался. Соглашение сайта (п. 5.3) предусматривает письменное разрешение на автоматический доступ и извлечение информации. Успешное чтение одной другой карточки не образует контрольную выборку; её цена отличалась от поискового индекса, поэтому поисковые выдержки не использованы как источник текущих цен.

Для разрешённой свежей выгрузки добавлен [шаблон manifest](fresh_validation_manifest.template.json). Нужны подтверждение происхождения и даты наблюдения, SHA-256 исходного CSV, ссылки и адреса, полная цена предложения KZT, восемь признаков и ЖК (неизвестные значения остаются пропусками). JSON фиксирует проверенные человеком сведения, но сам по себе их не доказывает. Публикация, обновление репозитория и скачивание не заменяют дату наблюдения.

`fresh_validation.py` исключает известные идентификаторы из всех raw-строк января/марта и связи с полными очищенными историческими наборами. Группы строятся транзитивно по URL, прежним ключам квартир и нормализованной адресной сигнатуре без цены. Основной результат относится только к строкам с полным идентификатором; сомнительные строки сохраняются отдельно. Предположение об уникальности физических квартир остаётся эвристическим.

Входы и код фиксируются до чтения/прогнозов и повторно проверяются по SHA. Сохранённые January, combined и +ЖК оцениваются на одинаковых строках без fit. CSV, данные обучения, каталог и активная модель не перезаписываются. Команда и состав отчёта описаны в README.

## Независимый источник географии: OpenStreetMap, 13 октября 2026

Для проверки адресов использован открытый [снимок Казахстана Geofabrik](https://download.geofabrik.de/asia/kazakhstan-261012.osm.pbf): данные OSM по **12 октября 2026, 20:21:35 UTC**, скачан 13 октября. SHA-256 PBF: `cafe5698da867819c0166b484f345444f4ac2be7a862bdfa3f22ebcc706878e5`. Исходник и manifest находятся в `raw/osm_2026_10_13/`. Дата снимка и время изменения объекта OSM не являются датой обследования дома.

Сопоставление выполняется локально, без запросов геокодирования по каждому адресу. Объект должен иметь полный адрес и единственный допустимый контур жилого здания внутри административной границы Астаны [OSM relation 3087155](https://www.openstreetmap.org/relation/3087155). Улица и номер сопоставляются точно; разные языковые написания допускаются только при наличии обоих на одном объекте дороги. Сохраняются корпус, дробь и буквенный суффикс номера. Спорные районы, разные здания по одному адресу и невалидные конкурирующие объекты остаются отказами; названия не исправляются нечётким поиском.

Совпадение в OSM получает статус `osm_exact_address`, а не «официально проверено». Подтверждение адреса на карте не разрешает противоречия в ЖК, годе и этажности. Все совпадения и отказы записаны в [аудит](../reports/coordinate_enrichment_2026_10_13/report.html); только допустимые новые адреса попадают в `processed/verified_coordinates_2026_10_13/registry.json`. Исходные 197 точек обученного справочника не заменяются и сохраняют свой прежний статус внутренней согласованности.

Производный адресный справочник: **© [OpenStreetMap contributors](https://www.openstreetmap.org/copyright), [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/)**. В каждой записи сохранены URL, версия, время правки объекта и сведения о снимке; рядом с реестром находится `ATTRIBUTION.txt`. Это данные географии, не новые цены квартир. Повторное сравнение на мартовских строках не заменяет свежую контрольную выборку и не подтверждает точность на рынке октября.

Результат: 898 совпавших адресных ключей / 845 зданий; 550 новых допустимых ключей / 521 здание добавлены в модель. Разные подтверждённые написания могут вести к одному зданию. 277 новых совпадений с конфликтами характеристик оставлены на проверку, 71 относится к прежним точкам. Источник названия района остаётся архивным: проверена граница города, но не границы каждого района. Проверка 15 адресов с полными исходными тегами сохранена в `reports/coordinate_enrichment_2026_10_13/sample_verification.json`.

Приложение использует отдельный `models/verified_geo_2026/complex_coords.joblib` с `models/deployment/complex_coords_osm.json`: 197 прежних и 550 новых ключей, всего 747. Переобучения нет. На тех же 590 строках MAE составила 6,4409 млн ₸ против 6,4427 млн ₸, ошибок свыше 20% по-прежнему 129. География доступна для 28 строк вместо 8. Изменение точности очень небольшое. Критерий подключения зафиксирован до прогнозов; исходные артефакты сохранены. Аудит подключения — `reports/coordinate_enrichment_2026_10_13/integration.json`.
